# CalFresh Data Dashboard (Community Edition)

## Purpose

CDSS's official CalFresh Data Dashboard publishes valuable data, but wasn't built with advocacy work in mind. This project builds on it as an independent, publicly shareable tool: it consolidates California Department of Social Services (CDSS) CalFresh data into one place and presents it with the kind of interactive, filterable visualizations (by county, date range, category) that state and county stakeholders need to track access, outcomes, discontinuances, and churn.

This is a revival of visualizations Diana Jensen originally built and maintained in Tableau Public while working at the San Francisco Marin Food Bank. This version is designed to be self-updating and easier to hand off to a future maintainer.

## Architecture

Three pieces, deliberately decoupled so no single piece failing takes down the others:

1. **Data ingestion — Google Apps Script**, bound to a Google Sheet in Diana's Drive. Runs on a time-driven trigger (independent of any Cowork/Claude session — it keeps running whether or not anyone is actively working on this project). Each run: checks the three CDSS source pages for newly posted files, downloads and parses anything new, labels raw columns with human-readable names, appends/updates the data, and prunes anything outside the retention window (see below).
2. **Data layer — Google Sheets.** The source of truth. Deliberately chosen over a code-only pipeline so a non-engineer can open it, sort a column, filter to a county, and sanity-check a number without needing to touch any code. Published to the web (read-only) so the frontend can fetch it with no authentication.
3. **Presentation — a static site on Vercel.** Plain HTML/JS (no server) that fetches the published Sheet data and renders interactive charts with filter/dropdown controls. Fully public, shareable via a link, no login required — matching how the original Tableau Public vizzes worked.

We considered (and ruled out) two alternatives worth recording: running the scraper inside Cowork directly (not viable — Cowork's sandbox has no general internet access and can't fetch binary files from arbitrary domains), and putting everything inside Vercel via a serverless cron job (viable, but makes the data itself opaque JSON/blob storage instead of something Diana can casually inspect).

## Data Sources

| Source | What it covers | Format | Update cadence observed |
|---|---|---|---|
| [CalFresh Data Dashboard raw Excel](https://www.cdss.ca.gov/inforesources/data-portal/research-and-data/calfresh-data-dashboard) | Participation, demographics, timeliness, benefit accuracy, error rates, program reach — statewide + all 58 counties, monthly back to Jan 2014 | Single always-current `.xlsx`, 6 tabs (`Monthly`, `Point in Time`, `Quarterly`, `Annual`, `PRI`, `Updates`) | Roughly every 1–3 weeks, in batches by metric group (see the file's own `Updates` tab for CDSS's changelog) |
| [CF296](https://www.cdss.ca.gov/inforesources/research-and-data/calfresh-data-tables/cf296) | Applications received/approved/denied/withdrawn, expedited service timeliness, discontinuances, recertifications, ICT | One `.xlsx` per fiscal year (FY2016-17 through current). Three different formats across that span (see Key Decisions Log, 2026-07-16) — FY2020-21 onward is 135 numeric columns labeled generically ("Cell 1"..."Cell 135" or, pre-FY2025-26, just bare numbers) with real meanings reconstructed from merged header rows; FY2016-17 through FY2019-20 is a different, 123-column format kept in its own `CF296_Legacy` tab | Monthly within the current FY file |
| [CF18](https://www.cdss.ca.gov/inforesources/data-portal/research-and-data/calfresh-data-tables/cf-18) | Caseload "churn": SAR7/RRR timely/untimely/late/not-renewed, average days to process | One `.xlsx` per fiscal year (FY2020-21 through current), tidy rows, 68 numeric columns ("Cell 1"..."Cell 68"), with a real `DataDictionary` tab mapping each cell | Monthly within the current FY file |

All three sources apply CDSS's data de-identification rule: any cell that could identify an individual (raw count under 11) is replaced with `"*"` rather than a number. The pipeline treats `"*"` as a suppressed value (not zero) and carries it through as such — this matters for anyone doing math on the columns later.

## Schema Decision: Mirror Everything, Not a Curated Subset

We initially planned to hand-pick ~30-50 "advocacy relevant" metrics per source to keep the Sheet small. We ran the numbers instead: a full raw mirror of all columns, full available history, across all three sources comes to roughly **4.06 million cells** (Monthly tab ~2.68M + the four smaller Master tabs ~84K + CF296 backfill across 10 fiscal years ~930K + CF18 backfill across 6 fiscal years ~360K), against Google Sheets' 10-million-cell-per-spreadsheet ceiling. That's about 40% of budget, growing by roughly 367,500 cells/year at the current pace. So we're mirroring everything and properly labeling all 513 raw columns (303 + 142 + 68), rather than curating — more labeling work up front, but a much more complete and future-proof dataset, and it still fits comfortably.

## Retention Policy (so this never breaks)

Two safeguards, so nobody ever has to babysit the cell count:

1. **Rolling 25-year window**, recomputed on every run (today minus 25 years — never a hardcoded date). Given Monthly data starts in 2014, this doesn't prune anything until roughly 2039, and CF296/CF18 have even less history than that to begin with.
2. **Safety valve:** after each update, the script totals actual cell usage across the whole spreadsheet. If it exceeds 8,000,000 cells (80% of the cap), it automatically drops the oldest calendar year of data from the largest tab(s) first (Monthly, since it dominates cell count) — regardless of the 25-year window — and logs exactly what it pruned and why in the Sheet's own Pipeline Log tab and in this file's Key Decisions Log below.

- **2026-07-16** — Chose Google Sheets + Apps Script over an all-Vercel (cron + serverless storage) pipeline. Reasoning: Diana wants to be able to spot-check the data herself without needing engineering tools; a Sheet is directly inspectable in a way that JSON in blob storage isn't.
- **2026-07-16** — Chose a static Vercel site over a Cowork-hosted artifact for the public-facing dashboard, since the artifact's public-sharability model (whether a non-Claude-account visitor can open it) wasn't confirmed, and full public access with no login is a hard requirement here.
- **2026-07-16** — Decided to mirror all 513 raw columns across all three sources rather than curate a subset, after confirming the full mirror fits at ~40% of Google Sheets' 10M-cell cap. Tradeoff accepted: more upfront labeling work (mapping CF296/CF18's generic "Cell N" columns to real names) in exchange for a materially more complete dataset.
- **2026-07-16** — Adopted a rolling 25-year retention window plus an 80%-of-cap safety-valve auto-prune, so the pipeline can never silently break by exceeding the Sheets cell limit, even under unexpected future growth (e.g., CDSS adding more columns).
- **2026-07-16** — The consolidated Sheet lives in Diana's djconsults.com Workspace Drive (a folder shared with her personal Gmail account, which is what Cowork's Drive connector authenticates as), rather than in the personal account directly — keeps this a company/organizational asset rather than tied to one personal login.
- **2026-07-16** — Built change detection off the "Updated" date text already shown on each CDSS listing page, rather than downloading each file just to compare headers/hashes. Cheaper (no wasted 12MB downloads on unchanged weeks) and simpler.
- **2026-07-16** — CF296 actually has 135 "Cell N" columns, not 136 as CDSS's own header row count suggested at a glance — verified directly against the file before building the label dictionary in Labels.gs.
- **2026-07-16** — Diana flagged that Apps Script's default OAuth consent ("edit, create, and delete all of your Drive files / all your Sheets") was broader than the script actually needs. Rewrote it to request `drive.file` (files it creates itself only) and `spreadsheets.currentonly` + `spreadsheets.readonly` instead of full access — done by moving all reads of the temporary converted files off `SpreadsheetApp.openById()` (which needs broad access to open an arbitrary file by ID) and onto the read-only Sheets API (`Sheets.Spreadsheets.Values.get`), and switching the script's own writes to `getActiveSpreadsheet()` (which qualifies as "current" for a bound script) instead of `openById()` on its own ID.
- **2026-07-16** — First live run of `testDiscovery()` confirmed both the narrowed OAuth consent wording and correct discovery of all three sources (dashboard master + 10 CF296 fiscal years + 6 CF18 fiscal years). It also surfaced a real bug: CDSS's own HTML leaves some filenames' whitespace unencoded (e.g. "Master data PUBLIC ACCESSIBLE.xlsx", "CF296 FY 2025-26.xlsx"), which would likely have broken the actual file download. Fixed in `normalizeUrl_()` in `SourceDiscovery.gs`. Took two attempts: a plain ASCII-space regex (`/ /g`) didn't catch it — the actual whitespace character CDSS uses renders identically to a normal space but isn't one (likely U+00A0, non-breaking space) — so it was widened to `/\s+/g`, which JS's whitespace class covers. **Confirmed working on a live re-run**: all URLs now show correct `%20` encoding.
- **2026-07-16** — First live run of `runInitialBackfill()`: dashboard master and all 6 CF18 fiscal years ingested cleanly. CF296 only succeeded for the current year (FY2025-26). Diagnosed by requesting three real sample files (FY2024-25, FY2020-21, FY2019-20) rather than guessing, which revealed CDSS has used **three different CF296 formats** over the years the report has been posted:
  - **`current`** (FY2025-26+): `Data_External` tab, header row 6, columns labeled `"Cell 1"`..`"Cell 135"`.
  - **`dataExternalLegacy`** (FY2020-21 through FY2024-25): same tab and same 135 metrics/columns, but header sits one row higher (row 5) and columns are labeled with bare numbers (`"1"`..`"135"`, no "Cell" prefix).
  - **`finalData`** (FY2016-17 through FY2019-20): a completely different tab (`FinalData`), only 123 metrics (not 135), and different metadata columns (no County Code, no Report Month — just Date/Month/Year/County Name/SFY/FFY).

  Rather than force-fitting the 123-item legacy era into the 135-column current schema (which would leave 12 columns permanently blank and require guessing which old item corresponds to which new one), `IngestCF.gs` now auto-detects which of these three known layouts a given file uses (tries each variant's tab name, then searches a small row window for the real header), and the legacy era writes into its own **`CF296_Legacy`** tab with its own honest 123-column schema and its own label dictionary (`CF296_LABELS_LEGACY` in `Labels.gs`, built from that era's own `DataDictionary` tab). CF18 hasn't shown any format drift across its 6 available years, but is now expressed with the same variant-list structure for consistency, in case an older CF18 year is ever posted.
- **2026-07-16** — Second live run of `runInitialBackfill()` after the above fix still failed for FY2020-21 through FY2024-25: they turned out to have **123 metrics, not 135** — the initial fix wrongly assumed `dataExternalLegacy` shared the current year's 135-item schema just without the "Cell" prefix. Comparing the actual item text captured from those files ("1A. Online applications received during the month") against the `finalData`-era dictionary showed an exact match, meaning `dataExternalLegacy` and `finalData` are really the *same* 123-item schema, just moved into a different tab name/metadata-column convention along the way. Both now route into `CF296_Legacy` using `CF296_LABELS_LEGACY`; only the current year (FY2025-26, genuinely 135 items) writes to `CF296`.
- **2026-07-16** — All 10 CF296 years and all 6 CF18 years confirmed backfilled correctly. Along the way, two jobs failed with generic Google-side errors (a 502 and a "Service Spreadsheets failed" exception) that resolved on a manual re-run of `runInitialBackfill` — these look like transient infrastructure hiccups from doing many rapid xlsx conversions back to back, not real bugs. Added automatic retry (`CONFIG.MAX_JOB_ATTEMPTS`, `isTransientError_()` in Utils.gs) so the pipeline retries this specific error class up to 3 times on its own before giving up and logging a permanent failure, rather than needing a human to notice and re-trigger the backfill.
- **2026-07-16** — Weekly trigger (`installWeeklyTrigger`) confirmed running, and the Sheet confirmed published to the web — the `gviz/tq?tqx=out:csv&sheet=NAME` CSV export endpoint confirmed working end-to-end (tested by Diana, returned real CF18 data). Pipeline is now fully live and self-sufficient.

## Frontend Implementation Notes (Participation view)

Everything below documents how `participation_trend_prototype_demographic-layers.html` actually works, so picking it up cold in Cursor doesn't mean reverse-engineering it first.

**It's a single self-contained HTML file** — Chart.js loaded from a CDN `<script>` tag, all CSS in one `<style>` block, all JS in one `<script>` block at the bottom, no build step, no framework. This was a deliberate prototyping choice (fast to iterate on, easy to preview), not necessarily the right shape for the long run — now that it's moving into a real editor, consider whether it's worth splitting into separate CSS/JS files or introducing a lightweight bundler, especially once more topic-area views get added and there's shared code to factor out (the tooltip/axis/plugin patterns below are all currently copy-pasted per chart, not shared modules).

**The data is a static embedded snapshot, not a live fetch.** Near the top of the `<script>` block there's a single-line `const DATA = {...}` blob (roughly 800KB of minified JSON) containing `months`, per-county `series` (persons + yoy_pct), `county_meta`, `demographic_layers.overlays` (Participant Types toggles: child-only, dual Medi-Cal, Students, $ Issued), and `all_counties`/region metadata. This was extracted from a real download of CDSS's Master file (dated 2026-07-16 — see the page's own `.prototype-note` banner) plus a few CSV exports Diana pulled directly from the Sheet for series that needed richer detail (Total Issuances for $ Issued, the Student table). **Before this goes live for real users, this needs to become a `fetch()` against the published Sheet's `gviz/tq?tqx=out:csv&sheet=NAME` CSV endpoint at page load**, replacing the embedded blob — this was always the plan (see Architecture above), just deferred so prototyping could happen without needing live Sheet access from every environment. Whoever does this swap should also decide where the Feb-2019-data-gap nulling and any similar one-off corrections should live afterward (see the data-notes item below) — right now they're baked into the static snapshot and will silently disappear the moment it's regenerated.

**Editing the DATA blob by hand:** because it's one ~800KB line, most editors (including the tool Claude used all session) can't do a normal find-and-replace inside it. The pattern that worked repeatedly: a small Python script that reads the file, finds the `const DATA = ` line, `json.loads()` it, mutates the resulting dict, and writes it back with `json.dumps(data, separators=(',', ':'))` (compact, no added whitespace, to match the existing minified style) — see the file's git history / this project's session logs for examples if you're doing this in Cursor instead. Cursor's editor may simply handle a long line better than the tools used to build this so far; worth just trying normal editing first.

**Chart.js patterns used across all three charts, worth keeping consistent if you add a fourth:**
- `interaction: { mode: 'nearest', intersect: false, axis: 'x' }` — required because every line dataset uses `pointRadius: 0`; without this, tooltips only fire when the cursor lands on the exact (invisible) point pixel.
- Tooltip `backgroundColor: 'rgba(24, 27, 36, 0.97)'` (plus explicit `titleColor`/`bodyColor`) — Chart.js's default tooltip background is only 80% opaque and lets gridlines/reference lines show through as visual noise.
- Tooltip structure: a `beforeBody` callback carries the one-time shared context line ("The % change... between DATE and DATE was:"), and each `label` callback collapses to a plain `"Name: value"` bullet — avoids repeating a full sentence per line when several lines are visible at once (an unavoidable consequence of `intersect:false`).
- `firstLastLabelPlugin` (a custom registered plugin, not built into Chart.js) draws the numeric value at each line's first/last data point, with leader lines to avoid overlap. It skips drawing entirely once more than 6 lines are visible at once (`chart.isDatasetVisible()`-aware) — past that, leader lines start crossing and reading as noise. This threshold is a judgment call, not a hard constraint; revisit if it feels wrong once real users are clicking around.
- `monthYearAxisPlugin` has a defensive `/^\d{4}-\d{2}$/` guard on its labels before trying to parse them as month strings — added after a real bug where it ran against the bucket chart's county-name labels and rendered the literal text "undefined" onto the chart.
- Standing rule from Diana (2026-07-31): **vertical axes always start at zero** on every chart, no exceptions — `min: 0` for always-positive metrics, `beginAtZero: true` for metrics that can go negative (like annual % change).
- Dual-axis pattern (used for the $ Issued overlay): give the overlay dataset `yAxisID: 'y1'`, exclude any `y1` dataset from the left axis's rescale-when-hidden logic, and conditionally spread a `y1` scale into `options.scales` only when that dataset is actually active.
- Region-aggregate lines (Annual % Change chart): `COUNTY_REGIONS`/`REGION_ORDER` map each county to one of 9 regions (hand-transcribed from Diana's original Tableau workbook — verbatim list is in `TODO.md`'s Region filter section). `computeAggregateRate()`/`computeAggregateSeries()` compute a population-weighted (sum-of-current ÷ sum-of-prior-year) rate, not a simple average of percentages — this matters, a straight average would overweight small counties. Region lines render dashed (`borderDash: [5, 3]`) to visually read as aggregates, not individual counties, matching the bucket chart's existing "Aggregate rate" convention.

**Known open issue, not yet fixed:** the multi-select filter boxes (Compare counties, Compare regions, Region, County Size, County) render wider than intended — two separate CSS fixes were tried 2026-08-14 (explicit `width` on the select, then wrapping it in a fixed-width `overflow:hidden` container) and neither worked. See the open TODO item in `TODO.md`'s Phase 4a section for exactly what was tried; next step is probably inspecting the live computed styles in browser DevTools rather than guessing from source, or rebuilding these as a custom checkbox-list component instead of native `<select multiple>` (which has known cross-browser listbox-sizing quirks).

**Feb 2019 data gap:** nearly every county's participant count drops sharply for exactly one month (Feb 2019) then fully rebounds — a real CDSS reporting anomaly, not a bug in this pipeline. It's nulled out in the embedded DATA blob (both the `persons` value and both `yoy_pct` legs that depend on it) for all 58 counties, plus a second, independent occurrence for Sonoma in Apr 2019. Documented in the page's own footer ("Data notes") and in `TODO.md`. This fix needs to move somewhere durable once the live-fetch swap happens (see above) — right now it disappears if the snapshot is ever regenerated.

## Deployment (Vercel)

This repo is meant to be pointed at directly from Vercel with zero build configuration — it's plain static HTML/CSS/JS, no framework, no server.

- `vercel.json` adds one rewrite so the root URL (`/`) serves `participation_trend_prototype_demographic-layers.html` — the file itself wasn't renamed to `index.html` to avoid touching a file Diana was actively reviewing mid-session; feel free to actually rename it to `index.html` and drop the rewrite once you're working in Cursor, that's the more conventional setup. As more topic-area views get built (Applications & Outcomes, Churn, etc.), either add more files + rewrite rules here, or restructure into real routes if this grows into something needing shared layout/nav.
- `package.json`/`package-lock.json`/`node_modules/` are local dev scaffolding (a `jsdom` install used for headless JS syntax/logic checks during this session, since the working environment couldn't run a real browser) — **not required for the deployed site itself.** Safe to delete if you want a leaner repo; `node_modules/` is already gitignored either way.
- Once connected, standard Vercel flow: push to GitHub, import the repo in Vercel, no build command needed (it'll auto-detect this as a static deployment).
